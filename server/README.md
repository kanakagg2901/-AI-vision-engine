# Server-Side: Privacy-Preserving Vision Agent

## What this is
The server half of the agent pipeline. It never receives raw pixels, screenshots,
or unredacted PII — only a **sanitized scene graph** the client (local ViT +
redaction pipeline) produces. It sends that scene graph to Claude with prompt
engineering that teaches the model to reason around redaction tokens, and
returns a strictly-typed JSON action for the extension to execute.

## Files
- `schemas.py` — Pydantic contract: `ScreenContext` (in), `AgentAction` (out).
  This is the privacy boundary spec — show this to judges as your "PII never
  crosses the wire" evidence.
- `prompts.py` — System prompt + scene-graph-to-text formatter + the tool
  schema used to force structured output.
- `llm_client.py` — Anthropic API call using **forced tool-use**, so you never
  parse free text / regex out of a chat response (avoids the classic flaky-demo
  failure mode).
- `main.py` — FastAPI app: `/session/start`, `/analyze`, `/session/end`, plus a
  defense-in-depth regex check that rejects payloads if something unredacted
  slipped through client-side.
- `demo_client.py` — Simulates the extension so you can demo the loop before
  the client-side ViT is finished.

## Run it
```bash
pip install -r requirements.txt
export ANTHROPIC_API_KEY=sk-...
uvicorn main:app --reload --port 8000
# in another terminal
python demo_client.py
```

## Design decisions worth mentioning to judges

**Why forced tool-use instead of asking the model to "return JSON":**
Free-text JSON parsing is the #1 source of demo failures under time pressure.
`tool_choice={"type": "tool", "name": "emit_action"}` guarantees a schema-valid
response every time, which also makes your latency more predictable (no retry
loops for malformed output).

**Why placeholders instead of real values for sensitive fields:**
When the plan requires typing a password/email, the model emits
`value_ref: "{{USER_SAVED_PASSWORD}}"` — a token the *client* resolves from its
own local, encrypted credential store. The real value is never generated by,
or sent to, the server. This is what makes the architecture genuinely
privacy-preserving rather than just "redact-then-still-send-secrets-eventually."

**Why a server-side regex safety net exists even though the client redacts:**
Judges evaluate "recall and precision of PII detection" — a two-layer defense
(client ViT detector + server pattern check) demonstrates you've thought about
failure modes of the local model, not just the happy path.

**Latency levers** (maps to the 15% end-to-end latency metric):
- `max_tokens=500` — actions are short, no need for a large budget.
- History capped to `MAX_HISTORY_TURNS` turns to prevent context growth from
  slowing later steps in a long task.
- Swap `MODEL` in `llm_client.py` to a smaller Claude model if you need to
  trade accuracy for speed during the live demo.

## What's still yours to build (client side, Person 2)
- Local ViT/detector (ONNX Runtime Web / Transformers.js) that produces the
  `elements` + `redactions` lists this server expects.
- The actual bounding-box blur/mask rendering in the browser.
- Extension code that executes the returned `AgentAction` (click/type/scroll)
  and resolves `value_ref` placeholders from a local, never-networked store.
- Sending `last_action_result` back on the next `/analyze` call so the agent
  loop can recover from failed actions (already supported by the schema).
